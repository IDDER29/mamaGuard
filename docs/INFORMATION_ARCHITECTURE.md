# MamaGuard — Information Architecture (Dashboard)

> Scope: this document defines the **Information Architecture (IA)** of the
> MamaGuard **clinician web dashboard** — its sitemap, navigation model, role
> access, screen hierarchy, and URL conventions.
>
> Stack reference: Next.js 16 (App Router, React 19) + Supabase. Auth is gated by
> `proxy.ts` (Next 16 middleware). Routes below are grounded in the actual files
> in `app/`.

---

## 1. Two surfaces

MamaGuard has **two distinct frontends**, and they must not be conflated:

| Surface | Audience | UI | Channel |
| --- | --- | --- | --- |
| **WhatsApp conversation** | The pregnant mother (patient) | No web UI — the entire experience is the chat thread | Meta WhatsApp Cloud API → `app/api/webhook/route.ts` → `lib/triage.ts` + `lib/generateMamaResponse.ts` |
| **Web dashboard** | Clinician / nurse, CHW, supervisor, admin | Next.js App Router under `app/dashboard/` | Browser (desktop + mobile) |

- The **mother never logs into the dashboard.** Her only interface is the Darija
  conversational agent ("Mama AI") over WhatsApp. The IA of that conversation
  (turn structure, danger-sign prompts, escalation flow, voice notes) is **out of
  scope here** and is specified separately in **`docs/CONVERSATION_DESIGN.md`**.
- **This document covers the dashboard IA only.** Where the two surfaces meet
  (e.g. a clinician reading the patient's WhatsApp transcript in Patient Detail,
  or triage alerts generated by the agent), the dashboard is the consumer of data
  the conversation produced.

## 4. Navigation model

### 4.1 Desktop — left sidebar (current implementation)

Defined in `components/dashboard/DashboardSidebar.tsx` (rail hidden below `lg`;
same content rendered in a slide-in drawer on smaller screens). Two groups today:

- **Primary navigation** (task-focused): Triage Board → Triage Queue → Worklist →
  All Patients → Education → Analytics.
- **Quick Access** (secondary): Messages, Protocols. Plus an **Emergency
  Resources** callout box (Emergency Contacts, Clinical Protocols) and a
  user-profile dropdown footer (Profile & Settings, My Schedule, Notifications,
  End Session / sign out via Supabase).

**Recommended primary/secondary split** (once §3 pages land):

- *Primary (always visible):* Triage Board, Triage Queue, Worklist, All Patients,
  Analytics.
- *Secondary (grouped under "Tools"):* Messages, Education, Protocols, Emergency.
- *Admin (role-gated, only for supervisor/admin):* Users & Roles, Facilities,
  Audit Log.
- *Footer:* Settings, Notifications, Sign out.

### 4.2 Mobile — recommended bottom-tab bar

CHWs and field nurses work primarily on phones. A persistent **bottom-tab bar**
should expose the **4 field-critical destinations**, replacing the slide-in drawer
as the primary mobile nav:

| Tab | Route | Icon (lucide) |
| --- | --- | --- |
| **Triage** (queue) | `/dashboard/alerts` | `Siren` |
| **Worklist** | `/dashboard/chw` | `ClipboardList` |
| **Patients** | `/dashboard/patients` | `Users` |
| **Search** | command palette / `/dashboard/patients?q=` | `Search` |

Everything else (Analytics, Education, Settings, Admin) lives behind a "More"
overflow or the existing drawer.

### 4.3 Command palette (⌘K / Ctrl-K)

For power users (clinicians, supervisors): a global palette to jump to any patient
by name/phone, jump to a route, or run an action (e.g. "register patient", "export
report"). This is the fastest path to a Patient Detail page without navigating the
patient list.

### 4.4 Breadcrumbs

Show on detail / nested pages so deep links are orientable:

- `Patients › {patient name}` on `/dashboard/patients/[id]`
- `Patients › Register` on `/dashboard/patients/new`
- `Admin › Users` on `/dashboard/admin/users`

Top-level pages (`/dashboard`, `/dashboard/alerts`, etc.) need no breadcrumb.

## 5. Roles → access matrix

Access levels: **none** / **read** / **write** (write implies read).

| Role | WhatsApp conversation | Triage Board `/dashboard` | Triage Queue `/dashboard/alerts` | Worklist `/dashboard/chw` | Patients `/dashboard/patients` | Patient Detail `[id]` | Analytics | Education `/content` | Admin `/admin/*` | FHIR / Reports export |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| **Mother** (WhatsApp only) | write (her own thread) | none | none | none | none | none | none | none | none | none |
| **CHW** | none | read | read (assigned) | write (own tasks) | read (assigned) | read + add notes | none | read | none | none |
| **Clinician / Nurse** | read transcript; manual reply | write | write | write | write | write | read | read | none | read (own facility) |
| **Supervisor / Program manager** | read transcript | write | write | write | write | write | read (aggregate) | write | write (users, facilities) | read |
| **Admin** | read (support) | write | write | write | write | write | read | write | write (all) | write |
| **Integration / Analyst** | none | none | none | none | none | none | read (aggregate) | none | read (audit) | read (FHIR `/api/fhir/*`, `/api/reports/export`) |

> ⚠️ **Gap — roles are not enforced in code today.** `proxy.ts` only checks
> *authenticated vs. anonymous* (and skips entirely when `DISABLE_AUTH=true`).
> There is no role concept in the schema beyond `patients.assigned_chw`
> (a per-patient assignment, not an RBAC role). RLS in `schema.sql` grants any
> authenticated clinician full access. The matrix above is the **target state**;
> implementing it requires a `role` on the user/clinician record, server-side
> enforcement (not just hiding sidebar links), and RLS policies keyed off role +
> facility + `assigned_chw`.

## 6. Information hierarchy per key screen

Priority = what the clinician's eye should hit **first → last**. Listed top-to-bottom.

### Triage Board — `/dashboard` (`app/dashboard/page.tsx`)
1. **Critical patients** (risk_level `critical` → red cards) — highest visual weight, top of the board.
2. **Warning patients** (risk_level `high` → mapped to `warning`).
3. Per-card glance: name, gestational week, the matched danger sign / alert message, key metrics, "last update" recency.
4. Board summary counts (total / critical / overdue) and search + filter tabs.
- **Primary actions:** open patient (→ Detail), refresh, register new patient. Per-card quick contact (call / message).

### Patient Detail — `/dashboard/patients/[id]` (server component)
1. **Risk banner + danger signs** — current `risk_level` and the triage findings driving it (never downgraded by the LLM).
2. **Patient identity & pregnancy status** — name, phone, gestational week / progress %, assigned CHW.
3. **Active alerts** (from the `alerts` table) — what needs action now.
4. **Conversation transcript** — the WhatsApp message history (the bridge to the other surface).
5. **Medical history / clinician notes** (`medical_history.notes`).
- **Primary actions:** escalate / mark handled, add clinical note, send a manual WhatsApp message, view FHIR export.

### Worklist — `/dashboard/chw` (`app/dashboard/chw/page.tsx`)
1. **Overdue / due-today tasks** — sorted by urgency, then due time.
2. **Assigned patients** needing a check-in (driven by `assigned_chw` + check-in cadence).
3. Completed / dismissed items (collapsed).
- **Primary actions:** complete task, open patient, log a visit / call.

### Analytics — `/dashboard/analytics` (`app/dashboard/analytics/page.tsx`)
1. **Headline KPIs** — patients monitored, alerts raised, escalations, response time.
2. **Risk distribution & trend over time** (recharts).
3. **Coverage / engagement** — message volume, check-in completion, CHW workload.
4. Breakdown filters (date range, facility, CHW).
- **Primary actions:** change time range / facility filter, export report (`/api/reports/export`).

## 7. URL & deep-linking conventions

- **Patient detail by id:** `/dashboard/patients/{uuid}` — canonical deep link to a
  single patient. Used as the click target from Triage Board cards, Triage Queue
  alert rows, and Worklist tasks.
- **Deep links from alerts / worklist:** every alert and task should link directly
  to `/dashboard/patients/{id}` (optionally `#alert-{id}` or `?tab=conversation`
  to scroll to the relevant section), so a clinician lands in context with one tap.
- **Query-param filters (shareable, bookmarkable):**
  - List filter/search: `/dashboard/patients?q=...&risk=critical&chw={id}`
  - Triage queue: `/dashboard/alerts?status=open&urgency=critical`
  - Analytics range: `/dashboard/analytics?from=YYYY-MM-DD&to=YYYY-MM-DD&facility={id}`
  - Filters belong in the URL (not just component state) so views are linkable in
    handoffs and reload-safe.
- **IDs:** use the Supabase `patients.id` UUID in URLs; never the phone number
  (PII in URL/history). Phone is a lookup key, not a route segment.
- **Auth redirects:** `proxy.ts` redirects unauthenticated `/dashboard/*` to
  `/login`; on success, return the user to the originally requested deep link
  (add a `?redirect=` / `?next=` param — not implemented yet).

## 8. Open IA questions

1. **Dashboard i18n & RTL.** The patient agent is Darija-first, but the dashboard
   is English-only. Should clinicians get Arabic (RTL) and French? This affects
   layout direction, the sidebar, and the proposed `/dashboard/settings/language`.
2. **Role enforcement.** Where does RBAC live — a `role` column + RLS, or an app
   middleware layer? Until decided, the §5 matrix is aspirational and the only
   real boundary is authenticated-vs-anonymous (and `DISABLE_AUTH` removes even
   that for demos).
3. **Where do notifications live?** Today the sidebar links to a non-existent
   `/dashboard/notifications` and badges are hard-coded. Is the notifications
   center a full page, a dropdown panel, or both? What's the source of truth —
   the `alerts` table, a realtime channel, or a new `notifications` table?
4. **"Triage Board" vs "Triage Queue" naming.** `/dashboard` and
   `/dashboard/alerts` use confusingly similar labels. Clarify the distinction or
   rename one.
5. **Messages surface.** Should clinicians read/reply to WhatsApp threads inside
   the dashboard (`/dashboard/messages` over `/api/whatsapp/send`), and if so how
   does that interact with the autonomous "Mama AI" agent (handoff / takeover)?
6. **Facilities & multi-tenancy.** There is no facility model yet. Admin
   facilities management, per-facility data scoping, and analytics breakdowns all
   depend on introducing a `facilities` entity and linking patients/clinicians to
   it.
7. **Dead links cleanup.** Decide per §3 whether to build, redirect, or remove the
   six 404-ing sidebar links so the nav never points at nothing.
